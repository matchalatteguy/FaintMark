Recommendation: build with TrustMark Q

Use TrustMark Q at default strength, with its strongest built-in error correction, behind a small local browser interface. Keep recipient records in SQLite. All image processing runs on this Mac; no hosting, paid API, account or subscription is required.

TrustMark recovered the exact ID in 435/450 routine cases (96.7%). PixelSeal recovered 354/450 (78.7%) at default strength and 390/450 (86.7%) at 1.4× strength. That stronger PixelSeal setting had nearly the same median image PSNR as TrustMark: 43.54 versus 43.31 dB. TrustMark remained ahead when the image-quality budget was approximately matched.

Both were quick enough on this Apple M2 Max: median TrustMark embedding was about 22 ms and extraction about 11 ms, with a warm model. TrustMark's tested Q encoder and decoder downloads total about 65 MB; the supplied PixelSeal checkpoint download is about 1.24 GB. This compares supplied downloads, not minimum possible app sizes after optimization. The entire experimental environment is about 1.1 GB before models; a finished Python app will not be tiny just because its interface is simple.

The classical baseline recovered 25/450 routine cases, including failures without recompression. Its off-the-shelf default configuration is unsuitable here. This diagnostic baseline has no added error correction; it is not evidence that every classical watermark design would fail.

Smallest useful first app

  1. A double-click launcher opening a local page. One Python process, FastAPI for local uploads/downloads, and plain HTML/CSS/JavaScript. Bind only to 127.0.0.1 and use an unpredictable session token. No JavaScript framework, Electron shell or external server is needed.
  2. Create copies. Drop in one JPEG or PNG, enter one recipient per line, and export a ZIP of individually marked PNG copies. Preserve the original file byte-for-byte. Generate a cryptographically random 40-bit ID for every image-recipient export; enforce uniqueness in the local database.
  3. Identify a copy. Drop in the suspect file. Accept only a successfully corrected, exact registered ID; display the assigned recipient, original thumbnail and export date. Unknown or unreadable IDs produce “Inconclusive,” with no nearest-recipient guesses.
  4. Verify every saved export. Decode the actual output file before recording success. Apply a small local compression/resize preflight to each copy; show a clear caution for fragile images. The full A/B test found 15 routine TrustMark failures, primarily under chained shrinking/recompression, so a clean-file self-check alone is insufficient.
  5. Back up the recipient registry. Include original-file SHA-256, a reference thumbnail, watermark variant/schema and copy IDs. Make a portable local backup/export; database loss would otherwise erase the recipient mapping.

Start with RGB JPEG/PNG only, default strength and PNG exports. Show an original/marked preview so visible artifacts can be reviewed. The test does not establish complete invisibility, especially for smooth graphics. JPEG exports, HEIC, alpha channels and colour-profile preservation need their own checks before support is advertised.

What still needs platform validation

This test validates local feasibility and picks a sensible engine; it does not certify Discord, Instagram or WhatsApp compatibility. The next acceptance set is a few representative marked images sent through Discord attachments, Instagram posts/DMs, and WhatsApp standard/HD, then downloaded and decoded. No platform APIs or private account access were used. No content was posted or sent during this work.

Keep the first interface free of “works everywhere” claims. A recovered mark identifies an assigned copy. It does not establish legal ownership or prove that its assigned recipient personally reposted it.
